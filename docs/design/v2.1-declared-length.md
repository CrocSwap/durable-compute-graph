# DCG v2.1: executor-declared run length (proposal LX2)

**Status: proposed (2026-10-14), design only; not built.** The owner decided
on 2026-10-14 to design this now and build it when a workload needs it. The
first expected workload is qushta's shared-layer certificate check (a Lean
kernel checking the compiler-correctness proof and the SBF model, once per
compiler version), whose step count is known only after running it. Every
quantity is labeled **designed** or **estimated**. Basanos project rule 10
applies: this changes what a run commits and adds a dispute claim, so it
needs an owner decision and an independent adversarial review before program
code.

## 1. The problem

LX1 (`v2.1-lazy-expansion.md`) requires the run's schedule to be known before
it runs:
- the position count `T` is part of the machine parameters, whose digest the
  payer admits at `INIT_RUN` (LX1 program review H1);
- the transitions in each position follow a closed-form rule
  (`LxMachine::transitions_in(p)`), so anyone, including the program, maps a
  global coordinate to (position, transition) and back.

A computation that loops until it finishes (an interpreter, a proof checker,
a search) has no such `T`. Both sides must still agree on what coordinate `i`
means, or bisection is undefined.

## 2. What already works: a padded bound

No DCG change is needed for a computation with a known upper bound `T_max`:
- **The machine holds a sticky `halted` slot.** The transition that finishes
  the work sets it; every transition reads it, and once it is set every
  transition is the identity.
- **The payer admits `T = T_max`.** Every checkpoint after the halt has the
  same root, so the executor computes them by copying, and the checkpoint
  tree over identical tail leaves costs `O(log T_max)` hashes to build
  (**designed**).
- **The OUTPUT claim** opens the output slots against `R_T`, which equals
  the state at the halt.
- **Cost:** bisection is logarithmic, so doubling `T_max` adds about a
  quarter of a round at arity 16 (`log_16 2`). The real costs are choosing a
  bound in advance and sizing the challenge window for a full re-execution
  up to `T_max` (LX1 §5, H5).

LX2 is for computations where no useful bound exists, or where a loose bound
makes the windows impractically long.

## 3. Proposal

An LX2 run commits its length; the payer admits only an upper bound.

1. **The template** declares the machine (as in LX1), a maximum length
   `T_max`, and the machine's **halt slot**: one state slot whose value is
   nonzero exactly when the computation has finished. The machine must make
   the halt sticky (every transition is the identity once it is set); the
   admitter checks this, as it checks `transitions_in(p) >= 1` today.
2. **The payer** admits the parameters without the length: the parameters'
   digest covers the inputs and `T_max`, not `T`.
3. **The executor** commits `T` with the checkpoint root, `1 <= T <= T_max`.
   `COMMIT` derives the checkpoint coordinates from `T` and `k` exactly as
   LX1 does from the admitted length, and refuses `T` outside the bound.
4. **A new claim, `HALT`**, alongside `OUTPUT`: a challenger opens the halt
   slot against `R_T`. If it is zero, the run had not finished at the length
   the executor committed, and the challenger wins (C). If it is nonzero, the
   executor wins (E).
5. **Everything else is LX1:** the dispute opening, rounds, terminal replay,
   OUTPUT claim, bonds, endings and closes.

Why this is enough:
- **A length that is too short** (the executor stops before the work is
  done, for example to claim an early "accepted") leaves the halt slot zero
  at `R_T`, so `HALT` convicts it from one membership path.
- **A length that is too long** is harmless: after the halt every transition
  is the identity, so the extra checkpoints repeat `R_halt` and the outputs
  are the same. The executor gains nothing but a longer dispute, and the
  template's `T_max` bounds that.
- **A false halt** (the halt slot set at a transition that should not set
  it) is an ordinary wrong transition: the challenger bisects to it and the
  terminal replay convicts it.

So the length needs no special trust: it is checked by the same state root
that every other claim uses.

## 4. Every ending (designed)

| Ending | Outcome |
|---|---|
| `HALT` claim, halt slot zero at `R_T` | C wins; run refuted |
| `HALT` claim, halt slot nonzero at `R_T` | E wins; the challenger's bond to the executor |
| `HALT` opening malformed or late | As LX1 openings: refused without state change; a missed deadline is a timeout for the side that owed it |
| `T > T_max` or `T = 0` at `COMMIT` | Refused; no run to dispute |
| `T` longer than needed | No dispute possible on that ground: checkpoints after the halt are honest repeats |
| A wrong transition anywhere, including a false halt | LX1 bisection and terminal replay |
| Honest checkpoints, false outputs | LX1 `OUTPUT` claim |
| No dispute | Finalizes after the challenge window |

**Who profits by calling first:** only a challenger opens `HALT`, and only
the executor answers it; the rest is LX1's table.

## 5. Costs and limits (estimated)

- **Chain:** one 8-byte length in the run's committed root, one more claim
  kind of about the `OUTPUT` claim's size (one path against `R_T`).
- **Windows:** the challenge window must still cover a full re-execution,
  now up to `T_max`. Unlike the padded bound, a watcher can see `T` at
  `COMMIT`, but the window is fixed when the template is admitted, so this
  saves nothing unless the program sizes the window from `T` at commit, which
  would let an executor shorten the window with a short (and convictable)
  `T`. Open question 1.
- **Rounds:** `log_16(T / k)` plus the position's own schedule, as LX1.

## 6. Open questions

1. Should the challenge window be sized from the committed `T` rather than
   `T_max`? It shortens honest runs, but a lying short `T` then gets a short
   window. A floor tied to `T_max` might be the compromise.
2. Should the halt be a whole slot or a declared bit within one?
3. Does any planned workload need data-dependent transition counts *within*
   a position? This proposal keeps `transitions_in(p)` closed-form and puts
   all data dependence in the position count. A loop body that varies in
   size is modelled as more positions, with no-op transitions where a body
   is shorter.
4. The interaction with the load extension (LX1 §5) and the finality bound
   D(N), which LX1 has not yet derived either.

## 7. Before building

- An owner decision on this proposal and on open question 1.
- A Python reference first (the LX1 practice): the `HALT` claim and a toy
  machine with a data-dependent length, played honestly and with each lie in
  §4.
- The independent adversarial review (rule 10), over every ending in §4.
