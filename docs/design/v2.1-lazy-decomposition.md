# DCG v2.1 lazy decomposition (proposal LD1)

Status: **superseded by LX1** (`v2.1-lazy-expansion.md`, adopted 2026-10-03). Its Python reference was removed when LX1 merged; the exact attention arithmetic it prototyped lives in Basanos (`src/basanos/dcg/lazy_attention.py`). Originally: **Python reference and design prototype, 2026-10-03.** This proposal
extends the tag-227 v2.1 first-divergence game. It changes the v2.1 spec profile
and would need a new program implementation and independent adversarial review
before adoption. No chain handler or Rust code is part of this prototype.

The motivating measurement is recorded separately in Basanos at
`docs/experiments/v21-attention-witness-2026-10-03.md`. It finds that
revision-8 W=64 attention windows
exceed the v2.1 128 KiB witness cap, while fixed W=16 decomposition appears to
fit each step but puts billions of extra leaves in the committed trace. LD1
keeps one ordinary parent leaf per large operation and creates a second-level
trace only after a challenger makes a STEP claim against that leaf.

## 1. Scope and soundness target

An ordinary trace leaf continues to commit the StepSpec identity, input value
digests, output value digests, and state digests. It remains one position in
the outer step tree. A lazy leaf is eligible only when its StepSpec names an
LD1 decomposition. EDGE, STATE, or STEP against an eligible parent opens a
second-level first-divergence game. Other outer claims keep the existing v2.1
rules.

The executor commits an indexed subtrace whose first inputs and initial state
are tied to the parent statement and whose final outputs and state are tied to
the parent statement. The challenger derives the honest subtrace using the
registered deterministic decomposition. If the parent output is false, an
executor cannot make every sub-step replay correctly while retaining both
boundary bindings: the first incorrect edge, state transition, or operation
must differ, or a boundary check fails. The nested game descends to the first
such divergence and judges one bounded sub-step.

This property depends on collision resistance, correct registry code, the
availability of the original parent inputs to the challenger, and a sound
source proof for each sub-step input. LD1 does not make an unavailable input
available. Large parent inputs must have an admitted chunk or LOG opening
scheme; a digest of a large byte string alone is not a range proof.

## 2. StepSpec declaration and decomposition registry

### 2.1 Explicit profile records

LD1 does not reinterpret a zero-reserved field in the current DCDS profile.
It requires a new spec profile. An eligible StepSpec keeps the exact
`kernel_id`, semantic version, ABI version, `decomposition_id`, and
`decomposition_version` identity already present in v2.1, and sets an explicit
`lazy_mode = 1` in the LD1 StepSpec profile. `lazy_mode = 0` means ordinary
replay. An LD1 `LazySpec` record (proposed spec-tree leaf type 10) is included
in `spec_root` and defines:

| Field | Meaning |
|---|---|
| kernel identity | 16-byte kernel id, semantic version, and ABI version |
| decomposition identity | nonzero id and version, exact registry dispatch key |
| count rule | registered count-function id/version and bounded parameters |
| accumulator scheme | scheme id/version, byte width (0–4096), signedness and canonical encoding |
| phase schedule | schedule id/version and per-index phase derivation |
| source map | deterministic parent-port, earlier-substep-output, parameter, and state sources for every sub-step input |
| limits | maximum sub-step count, witness bytes, and replay CU admitted for this shape family |

The count function is applied only to committed StepSpec shape and parameter
digests. It returns a positive `u32`; admission also checks it against the
LazySpec maximum. The shape fields, ordering, integer widths, overflow
behavior, accumulator encoding, phase schedule, and source map are versioned
consensus data. Runtime heuristics, executor-supplied counts, and host-native
iteration order are not inputs to count derivation.

The decomposition registry key is `(kernel_id, semantic_version,
abi_version, decomposition_id, decomposition_version)`. Registry entries
must agree with the committed count rule, accumulator scheme, phase schedule,
source map, and bounds. Missing or duplicate identities refuse admission.
Changing arithmetic or source selection requires a new decomposition version.

### 2.2 Sub-step statement

An LD1 sub-step leaf commits its index, phase, kernel identity and version,
ordered input value digests, prior-accumulator digest, ordered output value
digests, and next-accumulator digest. The witness bytes and large input values
are not stored in the leaf. The per-sub-step input source is derived from the
committed source map. A source can be a parent StepSpec port, an earlier
sub-step output, a parameter, or the accumulator chain. Each source is opened
with the corresponding value proof, chunk proof, or LOG proof.

The first record's input digests must equal the declared initial sub-step
inputs; the initial accumulator must equal the declared initial state (or the
parent's prior state). For every later record, the source opening must equal
the named earlier output and its prior-accumulator digest must equal the
previous record's next-accumulator digest. The last record's output digests
and state must equal the parent's committed outputs and next-state digest.

## 3. On-demand subtrace commitment and binding

Only after an outer STEP claim does E submit a subtrace descriptor and root.
The domain-separated root commits exactly `count(shape)` leaves in index
order. Its tree node domain is `dcg.lazy.node.v1\0`, its empty leaf is
`dcg.lazy.empty.v1\0`, and each record is leaf-hashed with
`dcg.lazy.substep.leaf.v1\0`. The descriptor
commits:

- the exact parent step leaf hash (the outer dispute already authenticates its
  ordinal and run/spec context);
- StepSpec kernel, semantic, ABI, and decomposition identities;
- the LazySpec identity and shape digest;
- count and accumulator scheme, with the phase schedule and source map
  resolved through that committed LazySpec identity;
- digest of all parent input digests and of the first sub-step's inputs;
- initial accumulator digest and final parent-output/state digests.

The descriptor and root are committed together in the nested-dispute state.
The root-submission action also opens the first and last records against that
root. The chain checks the descriptor against the authenticated parent
StepSpec and leaf; checks first input and initial-state bindings; and checks
last output and final-state bindings. Interior source and accumulator edges
are checked as the challenger descends. A count, identity, shape, endpoint,
or commitment mismatch is a boundary/shape loss for E.

This commitment is deliberately absent from the document's original trace.
If no one disputes the parent STEP, E does not build or post the subtrace.
When challenged, E must produce it before the root deadline. Withholding the
root loses by timeout. This moves the cost from every committed execution to
the subset of parent operations that receive STEP challenges; it does not
remove the work needed to build an honest subtrace during a dispute.

## 4. Nested phases, claims, and deadlines

The outer game first resolves the existing STEP_DESCEND path and identifies
the parent leaf. The outer STEP claim then enters LD1:

```text
AWAIT_SUBTRACE_ROOT(E)
  AWAIT_SUBTRACE_NODES(E) -> AWAIT_SUBTRACE_PICK(C)  (repeat by reveal depth)
  AWAIT_SUBSTEP_LEAF(E)
  AWAIT_SUBSTEP_CLAIM(C)
  AWAIT_SUBSTEP_OPENING(E)     (only when source/state proof is required)
  AWAIT_SUBSTEP_WITNESS(C)     (EDGE, STATE, and STEP as required)
  RULED
```

`BINDING` and `SHAPE` can rule directly from authenticated descriptor/leaf
bytes. `EDGE` proves or refutes the selected input source; `STATE` proves or
refutes the prior-to-next accumulator link; `STEP` replays the registered
sub-step on authenticated input and prior-state bytes. A selected sub-step
may require multiple opening/witness submissions if its source map has
multiple independent values; the admitted profile bounds and commits this
count. The Python prototype models one opening and one witness submission.

Every phase has a stored deadline. An action is accepted at `now <= deadline`
and TIMEOUT only at `now > deadline`, matching the outer game. For a phase
with `bytes_due`, the base window is the v2.1 phase window:

```text
phase_window + ceil(bytes_due / write_rate) * write_slots
```

The LD1 maximum witness/opening sizes must be included in admission, staging
pre-funding, and deadline derivation. E-wait extensions use the outer run's
existing accounting and caps; a nested phase cannot create an unaccounted
deadline extension. The challenger window applies to root bisection and its
claim. Timeout semantics for each new phase are part of the Python tests.

For a root with `n` leaves and reveal depth `d`, the subtrace descent has at
most `ceil(log2(n) / d)` reveal/pick rounds. It then needs one leaf opening,
one claim, and only the claim-specific opening/witness phases. This is added
after, not instead of, the outer descent and its claim.

## 5. Composition with rulings, moot, bonds, and endings

LD1 is a nested ruling inside the already-open outer dispute. It creates no
second challenger bond and no second run sequence number. The final nested
ruling becomes the outer dispute's ruling: E wins only if the registered
subtrace and claimed sub-step are consistent; C wins on a proven lie, a
broken boundary, or E's timeout. The outer run's ruled-prefix, best-win,
refutation, payout, and close rules continue unchanged.

### Every ending

| Ending | Required outcome |
|---|---|
| Valid BINDING/SHAPE/EDGE/STATE/STEP claim | Apply the nested ruling to the outer dispute; pay bonds only through the existing v2.1 result. |
| Invalid claim against honest parent/subtrace | Rule E; C's bond follows the ordinary executor-win policy. |
| E misses root, node, leaf, or required opening deadline | TIMEOUT rules C; the outer dispute settles under the existing challenger-win policy. |
| C misses pick, claim, or required witness deadline | TIMEOUT rules E; C loses its bond under the existing policy. |
| Malformed E root descriptor, boundary opening, node reveal, leaf, or proof | Refuse malformed writes before state advance; E remains responsible until its deadline, then C wins by timeout. A cryptographically authenticated malformed leaf may be claimed as SHAPE and rules for C. |
| Malformed C claim/opening/witness | Refuse it without advancing the phase; C remains responsible until deadline, then E wins by timeout. |
| A lower-sequence dispute has already refuted the run | F1 mootness wins over timeout: later disputes become moot, their challengers are refunded, and E receives no challenger bond from them. A nested timeout must not override moot status. |
| Dispute has ruled or is moot | It closes only after `ruled_prefix` advances past it; a refuted run also waits for the existing pot settlement rule. `CLOSE_DISPUTE` releases both stage buffers and the ordinary dispute rent to recorded payers. |
| Run finalizes | Only after the challenge deadline, zero open disputes, and no refutation. An unfinished LD1 phase is an open dispute, so cannot be skipped. |
| Run closes | Existing settled-run and all-disputes-closed conditions apply. No nested account or staging rent may remain stranded. |

No LD1 transition can directly pay either party, change the best-win
sequence, finalize a run, or close a dispute. This keeps nested outcomes under
the v2.1 payout and moot rules. The table is the required test matrix for the
program port; this Python prototype tests the new phase timeout mapping and
the local claim outcomes, not the on-chain bond/prefix lifecycle.

### Who profits by calling first

| Permissionless action | First caller and incentives |
|---|---|
| Outer `OPEN_DISPUTE` | C chooses a nonce and pays the ordinary bond/staging rent. E cannot take it merely by calling later. A payer or bystander can protect the run by opening a dispute, at their own bond risk. |
| Submit subtrace root / reveal nodes | Only E can advance these E-owned phases. E benefits from posting early by ending the timeout exposure; C gains no payment from a valid early answer. |
| Pick / claim / witness | Only C can advance C-owned phases. C benefits by moving a known false trace toward a ruling; delaying risks its bond. A bystander cannot substitute for C. |
| `TIMEOUT` | Anyone may call after the strict deadline. The caller receives no separate bounty; the named silent party determines the ruling. Calling before or at the deadline is refused. |
| Advance prefix / settle / finalize / close | Anyone may call once prerequisites hold. These actions do not change the recorded ruling or pay the caller; rent goes to the recorded payer. A bystander can unlock finality without capturing another party's funds. |

The permissionless notes preserve the v2.1 incentives; they do not claim that
LD1 payouts have been independently reviewed. Rule 10 requires an independent
adversarial review before any change to endings or economics merges.

## 6. What the executor stores and recomputes

Before the run, E stores the ordinary trace as today, plus the inputs or
content-addressed availability needed to replay each lazy kernel. It need not
store a subtrace tree for every parent step. On an outer STEP challenge it:

1. loads or recomputes the parent operation's canonical inputs;
2. replays the registered decomposition in order, retaining SMALL accumulator
   state and required intermediate outputs;
3. creates the sub-step record hashes and second-level Merkle tree;
4. stages the descriptor, endpoint openings, then only the requested node,
   leaf, source opening, or witness as the game advances.

E may cache these objects after construction, but cache contents are not
trusted and can always be regenerated from authenticated inputs. The
challenger independently reconstructs the honest subtrace. For a large
decomposition this is O(n) local execution and O(n) record/tree hashing for
both parties, plus logarithmic on-chain descent and one bounded replay. The
input availability window must leave enough time for that honest computation;
the admission `honest_compute_slots` bound must account for nested
decompositions.

## 7. Cost model and program shape

Let `N` be outer trace leaves, `n` the challenged parent decomposition's
sub-step count, `d` reveal depth, `W` the largest selected-step witness, and
`s` the stage write size.

| Cost | Ordinary committed decomposition | LD1 lazy decomposition |
|---|---:|---:|
| Outer trace leaves | `N + (n−1)` for each decomposed parent | `N`; no per-parent subtrace leaves |
| Extra trace commitment | none | one on-demand root and descriptor per challenged parent |
| Honest off-chain work after challenge | ordinary challenger replay | E and C each execute/hash O(n) sub-steps; E may cache |
| On-chain descent | one outer bisection | outer bisection plus `ceil(log2(n)/d)` nested bisection |
| Selected replay witness | one ordinary step | one sub-step witness, bounded by admitted `W` |
| Staged witness writes | `ceil(W_parent/s)` | `ceil(W/s)` for selected sub-step plus bounded openings |

The v2.1 design uses 900-byte stage writes and caps a witness at 1 MiB. An LD1
profile must keep every sub-step witness under both the admitted per-op cap
and the program transaction-size cap. A large proof is staged as today; it is
not copied in full through one instruction.

For the Basanos K=10,240 estimate in the accompanying experiment, lazy
attention preserves the measured base outer trace of 28,039 leaves per
position (287,119,360 leaves, height 29 over the whole document). A single
head parent has 2,560 W=16 sub-steps (height 12). With reveal depth 4, that is
8 outer plus 3 nested reveal/pick rounds. The experiment estimates 30 control
transactions and 86 staged-witness writes for a total of 116 transactions
for one challenged parent; actual packet/account framing, source-opening
fragments, and on-chain execution are open. Those are estimates, not a chain
measurement.

### Candidate program changes (not implemented)

The existing outer tag-227 dispute owns the same challenger bond, run
sequence, and payout. Add nested phase subcodes or instructions for
`LAZY_ROOT`, `LAZY_REVEAL_NODES`, `LAZY_PICK`, `LAZY_REVEAL_LEAF`,
`LAZY_CLAIM`, `LAZY_SUBMIT_OPENING`, and `LAZY_SUBMIT_WITNESS`, plus reuse
`TIMEOUT` with a nested-phase discriminator. Reuse `D21S` staging for large
root descriptors and witnesses. Do not allocate one account per sub-step.

The outer dispute account needs bounded nested state: the subtrace root and
descriptor digest, count/tree height, current level and position, selected
claim, nested phase/deadline, and staged-buffer cursors. A 64–128 byte state
addition is a first sizing estimate; exact layout, alignment, and rent are
open. A separate nested PDA is an alternative if it makes account locking
safer, but its address must be derived from the outer dispute and it must close
with the parent. Header/endpoint bytes are staged or included in the root
instruction; no account stores all sub-step leaves. The program must add
registered-decomposition dispatch, domain-separated tree verification,
source-proof checks, checked arithmetic, nested timeout/moot guards, and
cross-language goldens. Every proposed instruction and account size is
unmeasured pending a Python/Rust interface spec and native/SBF implementation.

## 8. Open protocol questions

- Should a lazy spec be a DCDS v2 profile leaf or a separate template-bound
  manifest, and how is its root made unambiguous at run admission?
- What exact source-proof interface lets a sub-step authenticate a slice of
  an ordinary parent input, an earlier sub-step output, and a LOG entry
  without importing application arithmetic into DCG?
- How is a four-phase reduction schedule represented compactly while keeping
  count and index-to-phase pure and auditable?
- What compute budget includes header/path validation, source openings,
  integer replay, and BPF dispatch overhead? Does a 1.16M-CU raw score proxy
  leave enough room?
- What witness, opening, and root sizes fit transaction and account limits?
- How are subtrace roots cached across duplicate challengers without making
  progress depend on shared mutable cache state?
- What `honest_compute_slots` admission bound and stage-growth rent are needed
  for very large `n`?
- Which exact tag/subcode and account layout should be frozen after the
  independently reviewed economics and endings pass?

test-only chunked dot product is in `lazy_toy.py`. Basanos attention arithmetic
is intentionally kept in Basanos and is not part of this document's generic
DCG kernel registry.
