# DCG v2.1 lazy expansion: checkpointed state chains (proposal LX1)

**Status: design draft for owner review (2026-10-03).** Not implemented.
It supersedes LD1 (`v2.1-lazy-decomposition.md`) as the target for large,
repeated workloads such as Basanos documents. LD1's exact window arithmetic
carries over unchanged; its committed sub-trace does not. Every quantity is
labeled **measured**, **estimated** or **designed**. Basanos project rule 10
applies: this changes how disputes end, so it needs an owner decision and an
independent adversarial review before program code.

## 1. Summary

A run commits a **coarse chain of state roots**: one every `k` positions
(checkpoints), plus the final state and outputs. Nothing finer is committed
up front.

A dispute bisects **one flattened, fine-grained schedule** between two
adjacent checkpoints, where the lower state is agreed and the upper one is
disputed:
- **Each round,** the executor commits midpoint state roots, and the
  challenger picks the sub-interval where its own computed root first
  differs.
- **At the end,** the interval holds one finest-grained transition (one
  kernel step, or one attention window), and the chain replays only that
  step:
  - it opens the step's inputs as members of the agreed lower root;
  - it computes the outputs;
  - it checks that the upper root equals the lower root with those outputs
    written in.

There is one mechanism for every level. Segments, positions, kernel steps
and attention windows are only a coordinate hierarchy over the same
schedule, so no refinement step is needed and every level shares the same
endpoint roots. A dispute does not use separate EDGE, STATE and STEP claims:
membership in the agreed lower state proves every input. This design comes
from:
- checkpointed-commitment pass 2 (Basanos
  `docs/design/checkpointed-commitment-2-2026-09-30.md`): interactive
  state-root bisection, component state roots;
- LD1's exact attention decomposition (Basanos `src/basanos/dcg/lazy_attention.py`).

**Why it scales (estimated).** At K=10,240 the committed trace shrinks
from about 287 million step leaves to `K/k` checkpoint roots, so 2,560 at
k=4. Dispute rounds grow only logarithmically in the schedule length.
Dispute-time recompute is bounded by one checkpoint interval.

## 2. The machine

### 2.1 State

A run's state is one fixed **slot layout** declared by the template. Each
slot holds a value, and the state root commits every slot's value digest in
canonical slot order. The layout has three regions:

| Region | Contents | Lifetime |
|---|---|---|
| Carried | DeltaNet state pages per layer; the K/V cache per attention layer (append-only LOG, one slot per position); residual; sampler and entropy state; position counter and generated output | across positions |
| Position scratch | every value a position's kernel steps produce and later read within the same position: one slot per (body step, output port) | empty at every position boundary |
| Step scratch | accumulators and per-window intermediates of a decomposed step (for example the score max, exp sum, probabilities and P·V numerator) | empty at every step boundary |

- **Root.** The state root is a binary Merkle root over the slot table,
  domain-separated by region and slot kind. Slot indices are a pure
  function of the template.
- **Empty slots.** An empty slot is a distinguished leaf. That keeps "empty
  at a boundary" checkable: a position-boundary state has empty scratch
  regions by construction, and the replay of the last step of a position
  must leave them empty.
- **Incremental hashing.** Content digests of large carried components
  (DeltaNet pages) are page-tree roots, so unchanged pages carry forward
  without rehashing (pass 2 §2.1).

### 2.2 Schedule and coordinates

The **finest transition** is one replayable unit:
- an ordinary kernel step whose witness and compute fit one dispute
  transaction;
- or one window of a decomposed step (the 16-position attention windows in
  four phases, exactly as in LD1).

The schedule of position `p` is the template's body steps in order, with
each decomposed step expanded into its windows. The number of windows can
depend on `p` (attention covers `p+1` positions), through a closed-form
count rule the template declares.

The **global coordinate** of a transition is its index in the flattened
schedule. The template makes the per-position count a closed-form function
of `p`, so anyone, including the program, can map a coordinate to
(position, body step, window) and back. A segment's coordinates are summed
over at most `k` positions.

### 2.3 Transition rule

Each finest transition, which the template defines:
1. reads a declared set of slots: its inputs, opened from the lower root;
2. reads committed constants: weights, opened against the template's
   constant roots, as v2.1 does today;
3. applies one registered, integer-exact kernel; Basanos's kernels stay in
   Basanos and register through the application manifest;
4. writes a declared set of slots, and clears the scratch slots that are no
   longer live.

A position's transition is the composition of its finest transitions, and a
segment's is the composition of its positions. Nothing at a coarser level is
judged directly, so there is nothing to keep consistent between levels.

## 3. Commitment

Before the challenge window opens, the executor commits a descriptor and
roots:
- the template, model and constant roots, the machine version, the slot
  layout version, `k` and the count-rule identity;
- `R_0`, the initial state root. It is derived from the admitted inputs
  (prompt, entropy), and anyone recomputes it;
- `R_k`, `R_2k`, …, and `R_T`, where `T` is the document length;
- the outputs, bound to `R_T`.

The checkpoint list is a fixed-length array of roots in the run account (or
a staging account for long documents) whose length the template fixes. The
run root that the existing v2.1 `COMMIT` stores is the hash of that array
and the outputs. `R_0` is not trusted from the executor: the program
recomputes it from admitted inputs at commit, or the first dispute round
checks it.

## 4. The dispute game

### 4.1 Opening

A challenger opens the dispute against two adjacent checkpoints, `j-1` and
`j`, where by its own computation `R_(j-1)` agrees and `R_j` differs. The
chain records the interval as global coordinates `[lo, hi]`, with roots
`R_lo = R_(j-1)` and `R_hi = R_j`. Choosing a pair costs the challenger
nothing on chain. A challenger that names a wrong pair loses at the terminal
replay (§4.3).

### 4.2 Rounds

With arity `a` (proposed 16; it trades rounds for midpoints per round):
1. The program derives `a-1` evenly spaced midpoint coordinates in
   `(lo, hi)`. The coordinates are fixed by the interval; the executor does
   not choose them.
2. The executor commits the `a-1` midpoint roots, or a staged list for
   large `a`, before its deadline. The commitment is immutable.
3. The challenger names the first sub-interval whose upper root differs
   from its own computation. The chain checks only that the index is in
   range; it cannot check the challenger's computation.
4. The interval shrinks to that sub-interval, which keeps an agreed lower
   root and a disputed upper root.

The game repeats until `hi - lo = 1`.

### 4.3 Terminal replay

At `hi = lo + 1`, the executor stages the opening for transition `lo`:
- membership paths, against `R_lo`, for every read slot and every written
  slot (a multi-proof);
- the read values;
- the constant openings.

The program then:
1. maps `lo` to (position, step, window) and loads that transition's
   declared reads, writes and kernel;
2. checks every membership path against `R_lo`;
3. replays the kernel exactly;
4. rebuilds the root with the written slots replaced and the dead scratch
   slots cleared, reusing the same paths;
5. compares the rebuilt root with `R_hi`.

If they match, the executor wins. A mismatch, or a malformed opening the
executor fails to replace in time, means the challenger wins. When the
transition is the document's last, the committed outputs are also checked
against the rebuilt state.

### 4.4 Soundness (sketch)

- **Lying executor.** The interval's lower root always equals the honest
  state, and its upper root differs. If a midpoint root is honest, the
  honest challenger moves right; if not, it moves left. Either way the
  invariant holds, whatever roots the executor picks, because each round's
  roots are committed before the challenger's choice. At the terminal step,
  the lower state is honest and the committed upper root is not, so honest
  replay from the lower state cannot rebuild it. The executor can win only
  by a hash collision or a verifier bug.
- **Lying challenger.** It can steer the interval anywhere. But the
  terminal transition is then an honest step from a committed lower root to
  a committed upper root, which replays correctly, so the challenger loses.
- **Silent party.** The party that owes the current phase loses by timeout.
  The F1 rule still applies: a dispute after the run's best win is moot,
  whatever its timeout would decide.

This assumes collision-resistant, domain-separated roots; a complete slot
layout (every value a later step reads is in the state); exact integer
replay; and timely inclusion within the deadlines. Pass 2 §3 has the
detailed argument; it carries over, because the layout here only adds
scratch regions with checked emptiness.

### 4.5 What is claimed: checkpoints, not every step

A run claims only its checkpoint states and its outputs. Suppose a
deviation inside an interval is overwritten before the next checkpoint (a
scratch value the next step overwrites, or a max that a later window
exceeds). Nothing committed differs, so there is nothing to dispute, and
the committed result is still correct. The toy tests show this: an uncleared
scratch slot is undisputable at `k=4`, but committed and convicted at
`k=1`. This is intended. It is also why the transition rule must clear dead
scratch: otherwise a stale scratch value at a checkpoint becomes part of
the claimed state.

### 4.6 Python reference (2026-10-03)

DCG `python/dcg/disputes_v21/lx.py` (the generic game: schedule
coordinates, checkpoint commitment, arity-`a` midpoints, picks, a canonical
multi-proof, terminal replay, timeouts), `lx_toy.py` (a toy machine with
carried state, an append-only log and a two-phase windowed step) and
`python/tests/test_disputes_v21_lx.py`. **Measured** (Python): 40 tests
pass, including:
- lies at position scratch, both window phases, the carried log and an
  uncleared boundary, each convicted at its own transition for k = 1, 4
  and 16 and arity 2 and 16;
- a lying challenger losing;
- every timeout;
- malformed midpoints and picks;
- forged, partial and padded openings refused.

Five planted bugs in the referee are caught. A sixth (letting an opening
omit slots) is equivalent in effect, because the canonical sibling-set
check still refuses it.

## 5. Composition with v2.1

LX1 is a new **commitment kind** for repeated-block templates. Enumerated
graphs and today's trace-committed templates keep the existing game
unchanged.

- **Bonds, sequences, best win, moot, ruled prefix, pay-pot, finalize,
  closes and rent: unchanged.** An LX1 dispute is an ordinary v2.1 dispute
  whose descent and claim phases are replaced by §4. It ends through the
  existing `rule`, so no new payout path exists.
- **The load extension applies to the executor's midpoint and opening
  phases.** Re-review follow-up B must land first, so that an executor's
  own puppet disputes cannot extend its windows.
- **Windows.** The midpoint phase window includes the executor's recompute
  bound, about `(span/a) × t_transition`. The opening window includes
  staging the multi-proof (`bytes_due / write_rate`).

### Every ending

| Ending | Outcome |
|---|---|
| Terminal replay rebuilds `R_hi` | Executor wins; the challenger's bond goes to the executor (existing rule) |
| Terminal replay mismatches, or the executor's opening is invalid at its deadline | Challenger wins; the run is refuted (existing rule) |
| The executor misses a midpoint or opening deadline | Timeout: challenger wins |
| The challenger misses a pick deadline | Timeout: executor wins |
| A malformed midpoint list or pick | Refused without state change; the sender may retry until its deadline |
| A dispute after the best win | Moot under F1, at any phase |
| The dispute names checkpoints that both match, or a wrong pair | The terminal step is honest, so the executor wins |
| A run with no dispute | Finalizes after the challenge window, as today |
| Closes | Existing dispute, run and cache closes; midpoint and opening staging closes with the dispute |

### Who profits by calling first

| Instruction | First caller |
|---|---|
| Commit midpoints, open terminal state | Only the executor can; posting early just ends its timeout exposure |
| Pick | Only the challenger can; delay risks its bond |
| `TIMEOUT`, `advance`, `moot`, `pay_pot`, `finalize`, closes | Anyone, as today; the caller gains nothing; rulings and payees come from recorded state |

## 6. What each party stores and recomputes

- **The executor** keeps enough to answer any midpoint inside any interval
  before its deadline:
  - the append-only K/V cache;
  - DeltaNet snapshots at a chosen spacing `s ≥ k`;
  - the inputs.

  Recompute from the nearest snapshot is at most `s` positions of work. At
  the dense DeltaNet state's 96 MiB per 4B snapshot (*estimated*, pass 2),
  `s=64` at K=10,240 is 160 snapshots, about 15 GB. A chosen `s` trades
  storage against response time.
- **The challenger** re-executes to find the first differing checkpoint,
  then the same as the executor inside the interval. Sampling watchers,
  which check only some segments, are a later mode.
- **The chain** stores only the checkpoint roots, the current interval and
  the current midpoint list.

## 7. Costs (estimated)

**4B profile:** 28,039 body steps per position (*measured*, the K=10,240
fixture). LD1 expands attention to 2,560 windows per head-op at K=10,240.

| | K=10,240, k=4 | K=10,240, k=64 | K=500,000, k=256 |
|---|---:|---:|---:|
| Committed roots | 2,561 | 161 | 1,954 |
| Happy-path state hashing | 2,560 × (96 MiB DeltaNet + K/V appends), about 250 GB | about 16 GB | about 190 GB |
| Today's revision-8 hashing at the same length, for scale | about 2.4 TB (8.1 GB per 35 positions, *measured*, extrapolated) | same | about 115 TB |
| Fine transitions in one interval | about k × (28k + windows) | about 64× more | about 256× more |
| Rounds at arity 16 | about 6 | about 7 | about 9 |
| Dispute transactions (2 per round, plus open, opening staging and settle) | about 20–30 | about 25–35 | about 30–40 |
| Recompute per round | at most k/16 positions of work | at most 4 positions | at most 16 positions |

**Measured, 35-position 4B plan** (Basanos
`docs/experiments/checkpoint-root-prototype-2026-10-03.md`; surrogate
state bytes in the proposed 58-component encoding, not real model state):

| k | Checkpoint hashing | Largest segment recompute | Segment-start state |
|---:|---:|---:|---:|
| 1 | 3.86 GB, 1.83 M SHA-256 calls | 805 operations | 110.6 MB |
| 4 | 1.00 GB, 0.47 M calls | 3,216 operations | 110.4 MB |
| 16 | 0.34 GB, 0.16 M calls | 12,828 operations | 110.4 MB |

The ROOT_ONLY comparator for the same document hashed 8.09 GB
(*measured*). The state root has 58 components: 24 DeltaNet rows, 24
convolution histories, 8 append-only K/V caches, a residual, and sampler and
output state, in 4 KiB pages. One DeltaNet page opening is at most
4,665 B.

**The DeltaNet state update needs subdivision, like attention.** The
largest `delta_state` step reads 4,325,888 B, far over the 131,072 B
witness cap. LX1 handles it the same way as attention: the template
declares it as a decomposed step whose finest transitions each touch a
bounded set of state pages (row-tiles of the recurrent update). The
decomposition must be exact for the integer recurrence.

Three rows are design levers rather than results:
- **Dense DeltaNet hashing dominates happy-path hashing.** Coarser `k`
  cuts it linearly. A machine version that hashes DeltaNet incrementally
  (only touched pages) would cut it further.
- **The opening size is bounded by the widest finest transition:** a W=16
  window with 16 K/V slots of 4 KiB each, plus paths, about 77 KB. That
  fits the 128 KiB staging cap.
- **Terminal compute** is the replayed kernel (at most about 1.16M CU
  measured for the revision-8 W=16 score window) plus multi-proof hashing
  (about log₂(slots) hashes per read and write). It must be measured before
  `k` and the window size are frozen.

## 8. Program shape (designed, not built)

- **Tag 227 subcodes:**
  - `LX_OPEN` (names the checkpoint pair);
  - `LX_MIDPOINTS` (executor; staged when long);
  - `LX_PICK` (challenger);
  - `LX_OPENING` (executor; staged);
  - `LX_REPLAY` (anyone, after the opening);
  - timeouts reuse `TIMEOUT` with LX phases.
- **Dispute state:** about 120 bytes for the interval, both endpoint roots,
  the midpoint-list digest, the arity, the phase and the deadline. The run
  account stores the checkpoint array, or its root plus a staged array for
  long documents.
- **The application manifest registers:**
  - the slot-layout version;
  - each body step's reads, writes and kernel;
  - the count rule;
  - the decomposed steps' window kernels (Basanos's attention phases).

  DCG ships only the mechanism and a toy machine.

## 9. Owner decisions

1. **Adopt LX1** (checkpointed state chains with one flattened bisection)
   as the v2.1 target for Basanos documents, superseding LD1's committed
   sub-trace.
2. **`k` per document within template bounds,** as approved for pass 2, and
   arity 16.
3. **The executor's snapshot policy is off-chain:** a recommended `s`,
   documented, not enforced.
4. **Keep i64 DeltaNet state for now** (pass 2 decision). Incremental
   DeltaNet hashing is a later machine version.

## 10. Open questions

- The exact slot layout for the 4B model, and slot liveness (which scratch
  slots each step clears). The prototype's 58-component encoding is the
  starting point.
- **The DeltaNet subdivision:** an exact row-tiled decomposition of
  `delta_state`, so each finest transition fits the witness cap and compute
  budget.
- **Real-state roots and Mac replay timings:** the prototype used surrogate
  bytes because the V7 artifact needs about 4.3 GB of weights, over its
  memory cap.
- Multi-proof encoding and its CU at the terminal replay.
- Mapping coordinates to transitions on chain: the closed-form count rule's
  arithmetic, and its cost for `k` up to 256.
- Long checkpoint arrays: K=500k at k=256 is about 62 KiB of roots, staged
  but fine.
- How LX1 templates are admitted: the slot layout and step read and write
  sets are new template records, trusted subjectively, as the admission
  cursor decision allows.
