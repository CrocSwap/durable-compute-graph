# DCG v2.1 lazy expansion: checkpointed state chains (proposal LX1)

**Status: adopted (2026-10-03) and implemented** on tag 227 (subs 23 to 26;
`crates/dcg-program/src/disputes_v21_lx.rs`), with the pure core in
`dcg-disputes::lx` and the Python reference. Native ProgramTests pass (SBF
passed before the review fixes)
with a registered toy machine; the program review's fixes are in §12. No
application machine (Basanos) or testnet run yet. Constants (weights) in
openings are built (§13, 2026-10-04).
It supersedes LD1 (`v2.1-lazy-decomposition.md`) as the target for large,
repeated workloads such as Basanos documents. LD1's exact window arithmetic
carries over unchanged; its committed sub-trace does not. Every quantity is
labeled **measured**, **estimated** or **designed**. Basanos project rule 10
applies: this changes how disputes end, so it needs an owner decision and an
independent adversarial review before program code.

## 1. Summary

A run commits a **coarse chain of state roots**: one every `k` positions
(checkpoints), plus the final state and outputs. Nothing finer is committed
up front.

A dispute bisects **one flattened, fine-grained schedule** between two
adjacent checkpoints, where the lower state is agreed and the upper one is
disputed:
- **Each round,** the executor commits midpoint state roots, and the
  challenger picks the sub-interval where its own computed root first
  differs.
- **At the end,** the interval holds one finest-grained transition (one
  kernel step, or one attention window), and the chain replays only that
  step:
  - it opens the step's inputs as members of the agreed lower root;
  - it computes the outputs;
  - it checks that the upper root equals the lower root with those outputs
    written in.

There is one mechanism for every level. Segments, positions, kernel steps
and attention windows are only a coordinate hierarchy over the same
schedule, so no refinement step is needed and every level shares the same
endpoint roots. A dispute does not use separate EDGE, STATE and STEP claims:
membership in the agreed lower state proves every input. This design comes
from:
- checkpointed-commitment pass 2 (Basanos
  `docs/design/checkpointed-commitment-2-2026-09-30.md`): interactive
  state-root bisection, component state roots;
- LD1's exact attention decomposition (Basanos `src/basanos/dcg/lazy_attention.py`).

**Why it scales (estimated).** At K=10,240 the committed trace shrinks
from about 287 million step leaves to `K/k` checkpoint roots, so 2,560 at
k=4. Dispute rounds grow only logarithmically in the schedule length.
Dispute-time recompute is bounded by one checkpoint interval.

## 2. The machine

### 2.1 State

A run's state is one fixed **slot layout** declared by the template. Each
slot holds a value, and the state root commits every slot's value digest in
canonical slot order. The layout has three regions:

| Region | Contents | Lifetime |
|---|---|---|
| Carried | DeltaNet state pages per layer; the K/V cache per attention layer (append-only LOG, one slot per position); residual; sampler and entropy state; position counter and generated output | across positions |
| Position scratch | every value a position's kernel steps produce and later read within the same position: one slot per (body step, output port) | empty at every position boundary |
| Step scratch | accumulators and per-window intermediates of a decomposed step (for example the score max, exp sum, probabilities and P·V numerator) | empty at every step boundary |

- **Root.** The state root is a binary Merkle root over the slot table,
  domain-separated by region and slot kind. Slot indices are a pure
  function of the template.
- **Empty slots.** An empty slot is a distinguished leaf. That keeps "empty
  at a boundary" checkable: a position-boundary state has empty scratch
  regions by construction, and the replay of the last step of a position
  must leave them empty.
- **Incremental hashing.** Content digests of large carried components
  (DeltaNet pages) are page-tree roots, so unchanged pages carry forward
  without rehashing (pass 2 §2.1).

### 2.2 Schedule and coordinates

The **finest transition** is one replayable unit:
- an ordinary kernel step whose witness and compute fit one dispute
  transaction;
- or one window of a decomposed step (the 16-position attention windows in
  four phases, exactly as in LD1).

The schedule of position `p` is the template's body steps in order, with
each decomposed step expanded into its windows. The number of windows can
depend on `p` (attention covers `p+1` positions), through a closed-form
count rule the template declares.

The **global coordinate** of a transition is its index in the flattened
schedule. The template makes the per-position count a closed-form function
of `p`, so anyone, including the program, can map a coordinate to
(position, body step, window) and back. A segment's coordinates are summed
over at most `k` positions.

### 2.3 Transition rule

Each finest transition, which the template defines:
1. reads a declared set of slots: its inputs, opened from the lower root;
2. reads committed constants: weights, opened against the template's
   constant roots, as v2.1 does today;
3. applies one registered, integer-exact kernel; Basanos's kernels stay in
   Basanos and register through the application manifest;
4. writes a declared set of slots, and clears the scratch slots that are no
   longer live.

A position's transition is the composition of its finest transitions, and a
segment's is the composition of its positions. Nothing at a coarser level is
judged directly, so there is nothing to keep consistent between levels.

## 3. Commitment

Before the challenge window opens, the executor commits (as built, in the
run's 176-byte root):
- the root of the checkpoint tree over `R_0`, `R_k`, `R_2k`, …, `R_T`, where
  `T` is the document length;
- a digest of its claimed outputs (the output slots of `R_T`), judged by the
  OUTPUT claim (§12, H2);
- the digest of the machine parameters (the inputs and the length), which
  must equal the run's input id that the payer gave at `INIT_RUN` (§12, H1);
- the position count and `k`. The executor chooses `k` within the template's
  `[k_min, k_max]`; it is not admitted by the payer, and it affects only
  dispute cost, not soundness.

The template commits the machine (kernel id and versions), the arity and the
bounds on `k` and positions.

What `COMMIT` checks (review H1, H2, H4):
- **Coordinates are derived, never supplied.** The checkpoint coordinates
  come from `k`, the machine's closed-form position starts and `T`. The
  checkpoint count is derived the same way.
- **`R_0` is checked, not trusted.** The machine computes the initial state's
  root from the admitted parameters (`LxBound::initial_root`); `COMMIT`
  verifies checkpoint 0 against it with one path. For Basanos the inputs
  (prompt, entropy) sit in an aligned input subtree, so this is a few hashes.
  An executor that ran from different inputs is refused at commit.
- **Runs are not repeatable without a distinguishing input.** The run
  address is derived from the template, the parameters' digest, the refs,
  the executor and the payer, and a receipt keeps the address. An identical
  run (same parameters, executor and payer) cannot be initialized twice,
  including a retry with the same executor after a refutation. Applications
  put a distinguishing field (a document or request id) in their parameters;
  Basanos does (LX1 re-review medium, 2026-10-03).
- **The roots live in program-owned accounts.** As built, the run's
  program-owned root commits one Merkle root over the checkpoint roots (tree
  `lxcheckpoint`) and a digest of the claimed outputs; a dispute opens the
  pair it names with two paths. This keeps COMMIT to one transaction at any
  length (K=10,240 at k=4 has 2,561 roots). Nothing is read back from an
  executor-writable buffer as a commitment; that class of bug was critical
  in the list-input review.

## 4. The dispute game

### 4.1 Opening

A challenger opens the dispute against two adjacent checkpoints, `j-1` and
`j`, where by its own computation `R_(j-1)` agrees and `R_j` differs. The
chain records the interval as global coordinates `[lo, hi]`, with roots
`R_lo = R_(j-1)` and `R_hi = R_j`. Choosing a pair costs the challenger
nothing on chain. A challenger that names a wrong pair loses at the terminal
replay (§4.3).

### 4.2 Rounds

With arity `a` (proposed 16; it trades rounds for midpoints per round):
1. The program derives `a-1` evenly spaced midpoint coordinates in
   `(lo, hi)`. The coordinates are fixed by the interval; the executor does
   not choose them.
2. The executor commits the `a-1` midpoint roots before its deadline. They
   are stored in the dispute account itself (15 roots, 480 B at arity 16),
   never in a staging buffer, and the commitment is immutable.
3. The challenger names the first sub-interval whose upper root differs
   from its own computation. The chain checks only that the index is in
   range; it cannot check the challenger's computation.
4. The interval shrinks to that sub-interval, which keeps an agreed lower
   root and a disputed upper root.

The game repeats until `hi - lo = 1`.

### 4.3 Terminal replay

At `hi = lo + 1`, the executor stages the opening for transition `lo`:
- membership paths, against `R_lo`, for every read slot and every written
  slot (a multi-proof);
- the read values;
- the constant openings (§13; not yet built: the first program cut opens only
  state slots).

The program then:
1. maps `lo` to (position, step, window) and loads that transition's
   declared reads, writes and kernel;
2. checks every membership path against `R_lo`;
3. replays the kernel exactly;
4. rebuilds the root with the written slots replaced and the dead scratch
   slots cleared, reusing the same paths;
5. compares the rebuilt root with `R_hi`.

If they match, the executor wins. A mismatch, or a malformed opening the
executor fails to replace in time, means the challenger wins. The committed
outputs are judged separately, by the OUTPUT claim against `R_T` (§12, H2).

### 4.4 Soundness (sketch)

- **Lying executor.** The interval's lower root always equals the honest
  state, and its upper root differs. If a midpoint root is honest, the
  honest challenger moves right; if not, it moves left. Either way the
  invariant holds, whatever roots the executor picks, because each round's
  roots are committed before the challenger's choice. At the terminal step,
  the lower state is honest and the committed upper root is not, so honest
  replay from the lower state cannot rebuild it. The executor can win only
  by a hash collision or a verifier bug.
- **Lying challenger.** It can steer the interval anywhere. But the
  terminal transition is then an honest step from a committed lower root to
  a committed upper root, which replays correctly, so the challenger loses.
- **Silent party.** The party that owes the current phase loses by timeout.
  The F1 rule still applies: a dispute after the run's best win is moot,
  whatever its timeout would decide.

This assumes collision-resistant, domain-separated roots; a complete slot
layout (every value a later step reads is in the state); exact integer
replay; and timely inclusion within the deadlines. Pass 2 §3 has the
detailed argument; it carries over, because the layout here only adds
scratch regions with checked emptiness.

### 4.5 What is claimed: checkpoints, not every step

A run claims only its checkpoint states and its outputs. Suppose a
deviation inside an interval is overwritten before the next checkpoint (a
scratch value the next step overwrites, or a max that a later window
exceeds). Nothing committed differs, so there is nothing to dispute, and
the committed result is still correct. The toy tests show this: an uncleared
scratch slot is undisputable at `k=4`, but committed and convicted at
`k=1`. This is intended. It is also why the transition rule must clear dead
scratch: otherwise a stale scratch value at a checkpoint becomes part of
the claimed state.

## 5. Composition with v2.1

LX1 is a new **commitment kind** for repeated-block templates. Enumerated
graphs and today's trace-committed templates keep the existing game
unchanged.

- **Bonds, sequences, best win, moot, ruled prefix, pay-pot, finalize,
  closes and rent: unchanged.** An LX1 dispute is an ordinary v2.1 dispute
  whose descent and claim phases are replaced by §4. It ends through the
  existing `rule`, so no new payout path exists.
- **The load extension applies to the executor's midpoint and opening
  phases.** Re-review follow-up B must land first, so that an executor's
  own puppet disputes cannot extend its windows.
- **Windows (review H5).** Both parties must recompute before they can act,
  so every LX window is sized from the run's `k`, the interval's largest
  position and the snapshot spacing `s`:
  - **The executor's midpoint window** covers recompute from the nearest
    snapshot across `(a-1)/a` of the current interval, not `span/a`. The
    first round is the most expensive.
  - **The challenger's pick window** covers its own recompute of the
    executor's midpoints. Using the ordinary 750-slot window would let a
    lying run finalize while honest challengers time out.
  - **The opening window** covers staging the multi-proof
    (`bytes_due / write_rate`).
  - **The challenge window** is at least one full re-execution of the run.
  - **The load extension for LX phases** is additive and uncapped, with
    `extend_slots ≥ worst-case interval recompute + answer` per open
    dispute. This is follow-up B's design, extended to recompute: a
    griefer opening N disputes on N pairs pays N bonds, and the honest
    executor gets time for N recomputes. The finality bound D(N) (v2.1
    §10.2) must be re-derived with it.

### Every ending

| Ending | Outcome |
|---|---|
| Terminal replay rebuilds `R_hi` | Executor wins; the challenger's bond goes to the executor (existing rule) |
| Terminal replay mismatches, or the executor's opening is invalid at its deadline | Challenger wins; the run is refuted (existing rule) |
| The executor misses a midpoint or opening deadline | Timeout: challenger wins |
| The challenger misses a pick deadline | Timeout: executor wins |
| A malformed midpoint list or pick | Refused without state change; the sender may retry until its deadline |
| A dispute after the best win | Moot under F1, at any phase |
| The dispute names checkpoints that both match, or a wrong pair | The terminal step is honest, so the executor wins |
| `R_0` differs from the admitted inputs | Refused at `COMMIT`; there is no run to dispute (H1) |
| The checkpoints are honest but the claimed outputs are not | `OUTPUT` claim: open the output slots against `R_T`; C wins on any difference (H3) |
| An empty checkpoint interval | Refused at open (L1) |
| The kernel fails on a verified opening | C wins: the committed lower state cannot lead to any committed upper root (L2) |
| The transition cannot replay within compute or witness limits | Must not exist: the CU and opening census at admission is a gate (M2) |
| A run with no dispute | Finalizes after the challenge window, as today |
| Closes | Existing dispute, run and cache closes; midpoint and opening staging closes with the dispute |

### Who profits by calling first

| Instruction | First caller |
|---|---|
| Commit midpoints, open terminal state | Only the executor can; posting early just ends its timeout exposure |
| Pick | Only the challenger can; delay risks its bond |
| `TIMEOUT`, `advance`, `moot`, `pay_pot`, `finalize`, closes | Anyone, as today; the caller gains nothing; rulings and payees come from recorded state |

## 6. What each party stores and recomputes

- **The executor** keeps enough to answer any midpoint inside any interval
  before its deadline:
  - the append-only K/V cache;
  - DeltaNet snapshots at a chosen spacing `s ≥ k`;
  - the inputs.

  Recompute from the nearest snapshot is at most `s` positions of work. At
  the dense DeltaNet state's 96 MiB per 4B snapshot (*estimated*, pass 2),
  `s=64` at K=10,240 is 160 snapshots, about 15 GB. A chosen `s` trades
  storage against response time.
- **The challenger** re-executes to find the first differing checkpoint,
  then the same as the executor inside the interval. Sampling watchers,
  which check only some segments, are a later mode.
- **The chain** stores only the checkpoint roots, the current interval and
  the current midpoint list.

## 7. Costs (estimated)

**4B profile:** 28,039 body steps per position (*measured*, the K=10,240
fixture). LD1 expands attention to 2,560 windows per head-op at K=10,240.

| | K=10,240, k=4 | K=10,240, k=64 | K=500,000, k=256 |
|---|---:|---:|---:|
| Committed roots | 2,561 | 161 | 1,954 |
| Happy-path state hashing | 2,560 × (96 MiB DeltaNet + K/V appends), about 250 GB | about 16 GB | about 190 GB |
| Today's revision-8 hashing at the same length, for scale | about 2.4 TB (8.1 GB per 35 positions, *measured*, extrapolated) | same | about 115 TB |
| Fine transitions in one interval | about k × (28k + windows) | about 64× more | about 256× more |
| Rounds at arity 16 | about 6 | about 7 | about 9 |
| Dispute transactions (2 per round, plus open, opening staging and settle) | about 20–30 | about 25–35 | about 30–40 |
| Recompute per round | at most k/16 positions of work | at most 4 positions | at most 16 positions |

**Measured, 35-position 4B plan** (Basanos
`docs/experiments/checkpoint-root-prototype-2026-10-03.md`; surrogate
state bytes in the proposed 58-component encoding, not real model state):

| k | Checkpoint hashing | Largest segment recompute | Segment-start state |
|---:|---:|---:|---:|
| 1 | 3.86 GB, 1.83 M SHA-256 calls | 805 operations | 110.6 MB |
| 4 | 1.00 GB, 0.47 M calls | 3,216 operations | 110.4 MB |
| 16 | 0.34 GB, 0.16 M calls | 12,828 operations | 110.4 MB |

The ROOT_ONLY comparator for the same document hashed 8.09 GB
(*measured*). The state root has 58 components: 24 DeltaNet rows, 24
convolution histories, 8 append-only K/V caches, a residual, and sampler and
output state, in 4 KiB pages. One DeltaNet page opening is at most
4,665 B.

**The DeltaNet state update needs subdivision, like attention.** The
largest `delta_state` step reads 4,325,888 B, far over the 131,072 B
witness cap. LX1 handles it the same way as attention: the template
declares it as a decomposed step whose finest transitions each touch a
bounded set of state pages (row-tiles of the recurrent update). The
decomposition must be exact for the integer recurrence.

Three rows are design levers rather than results:
- **Dense DeltaNet hashing dominates happy-path hashing.** Coarser `k`
  cuts it linearly. A machine version that hashes DeltaNet incrementally
  (only touched pages) would cut it further.
- **The opening size is bounded by the widest finest transition:** a W=16
  window with 16 K/V slots of 4 KiB each, plus paths, about 77 KB. That
  fits the 128 KiB staging cap.
- **Terminal compute** is the replayed kernel (at most about 1.16M CU
  measured for the revision-8 W=16 score window) plus multi-proof hashing
  (about log₂(slots) hashes per read and write). It must be measured before
  `k` and the window size are frozen.

## 8. Program shape (designed, not built)

- **Tag 227 subcodes:**
  - `LX_OPEN` (names the checkpoint pair);
  - `LX_MIDPOINTS` (executor; in the dispute account);
  - `LX_PICK` (challenger);
  - `LX_OPENING` (executor; the opening is staged in E's buffer, then
    frozen, and replayed and ruled in the same instruction as its final
    write, so no separate replay step is needed; review M5);
  - `LX_OUTPUT` (challenger; the output claim);
  - timeouts reuse `TIMEOUT` with LX phases.
- **Dispute state:** about 120 bytes for the interval, both endpoint roots,
  the midpoint-list digest, the arity, the phase and the deadline. The run
  account stores the checkpoint array, or its root plus a staged array for
  long documents.
- **The application registers its machine as code** (decided 2026-10-03,
  host). It implements `dcg_disputes::lx::LxMachine`, the Rust mirror of the
  Python `Machine` protocol:
  - `transitions_in(p)` and `position_start(p)`, closed forms;
  - `slots(p, i)`, the reads and writes of one transition;
  - `apply`, the integer kernel.

  The template commits the machine's id and version through the application
  manifest.

  DCG owns everything else: it locates a coordinate by binary search over
  `position_start`, checks it against `transitions_in`, and checks that the
  opening covers exactly the reads and writes. It verifies the multi-proof
  against the lower root, replays, rules (a kernel failure rules C), and
  rebuilds the upper root (`lx::replay`, `lx::output_claim`).

  A data-driven alternative was rejected: a tree of step descriptors with
  affine slot rules. Basanos's slot sets depend on position, chunk and head
  in ways a fixed descriptor format would have to keep growing to express.
  The machine's slot rules are already consensus code in the application's
  image, like its kernels.

  DCG ships the mechanism and a toy machine. The toy machine's Rust port
  (`crates/dcg-disputes/tests/lx_replay.rs`) reproduces the Python rulings.

## 9. Owner decisions

**Decided 2026-10-03:** LX1 is adopted as written. `k` is chosen per
document within the template's bounds, defaulting to 4, with arity 16.
Snapshots stay off chain, and DeltaNet state stays i64.

**Why every `k` tokens rather than every token.** Commitment size is not the
constraint: per-position roots at 500k tokens are 16 MB, and could be
committed through one Merkle root over them, with individual roots revealed
during a dispute. The constraint is hashing. DeltaNet carries dense latent
state between tokens, so every page changes at every position, and each
checkpoint rehashes about 96 MiB (4B, *estimated*). Hashing every position
cost 3.86 GB against 1.00 GB at k=4 on the measured 35-position document.
`k=1` remains available per document. Committing DeltaNet state without
rehashing it fully (for example, committing each position's update inputs)
is a later machine-version option.

The items as proposed:

1. **Adopt LX1** (checkpointed state chains with one flattened bisection)
   as the v2.1 target for Basanos documents, superseding LD1's committed
   sub-trace.
2. **`k` per document within template bounds,** as approved for pass 2, and
   arity 16.
3. **The executor's snapshot policy is off-chain:** a recommended `s`,
   documented, not enforced.
4. **Keep i64 DeltaNet state for now** (pass 2 decision). Incremental
   DeltaNet hashing is a later machine version.

## 10. Open questions

- The exact slot layout for the 4B model, and slot liveness (which scratch
  slots each step clears). The prototype's 58-component encoding is the
  starting point.
- **The DeltaNet subdivision:** an exact row-tiled decomposition of
  `delta_state`, so each finest transition fits the witness cap and compute
  budget.
- **Real-state roots and Mac replay timings:** the prototype used surrogate
  bytes because the V7 artifact needs about 4.3 GB of weights, over its
  memory cap.
- Multi-proof encoding and its CU at the terminal replay.
- Mapping coordinates to transitions on chain: resolved by the machine trait
  (§8). `locate` costs `O(log positions)` calls to `position_start`; its CU
  on SBF is not yet measured.
- Long checkpoint arrays: K=500k at k=256 is about 62 KiB of roots, staged
  but fine.
- How LX1 templates are admitted: the slot layout and step read and write
  sets are new template records, trusted subjectively, as the admission
  cursor decision allows.

## 11. Independent design review (2026-10-03)

Verdict: **adopt after fixes.** The bisection held under fuzzing: across
31 adaptive lying-executor cases and 20 lying-challenger seeds, the honest
side won every time. The holes were around it:

| Finding | Change |
|---|---|
| H1: a lying `R_0` was undisputable | `COMMIT` rebuilds `R_0` from an aligned input subtree (§3). Python: `admit_commitment` refuses a lying `R_0`, with a test |
| H2: the executor chose the checkpoint coordinates | Coordinates are derived; arrays of the wrong length are refused (§3). Python: test |
| H3: the outputs were not bound to `R_T` | Outputs are slots of `R_T`, plus a one-transaction `OUTPUT` claim (§3, endings). Python: test |
| H4: roots could live in rewritable staging | The checkpoint array lives in a program-owned run extension, and midpoints in the dispute account (§3, §4.2, §8) |
| H5: windows were undersized | Windows are sized from `k`, `s` and the interval, with an additive load extension for recompute (§5) |
| M1: gaps in the slot layout | The executor computes through the same slot-level transition function. A differential test replays every transition of the real K=35 document from slot state alone. Admission checks scratch liveness statically. "Empty means identity" accumulators get golden vectors |
| M2: compute and opening fit | A per-transition CU and opening census at admission is a gate. The score window measured 1.16M CU, plus an estimated 0.1M for proofs: tight. Cache read-only leaf hashes. Survey the weight openings of ordinary body steps and the DeltaNet tiles. Split the K/V slots by head pair (rows are 8 KiB) |
| M3: the DeltaNet subdivision | Row-local tiles look exact (estimated about 1,032 tiles per layer, about 25k more transitions per position). Verify against the integer kernel, including the 4,096-element core prefix and the clamp order |
| M4: K=500k is unsupported by measurement | Estimated storage per party: about 65 GB of K/V plus about 197 GB of snapshots at s=256. Windows grow to hours. Treat 500k as a scaling target, not a sizing |
| M5: endings and rule 10 | The rows above are added; opening and replay are fused. Moot, close and timeout combinations need tests before any program merge |
| L1: an empty interval convicted an honest executor | Refused at open. Python: test |
| L2: a malformed value crashed the referee | A kernel failure on a verified opening rules for C. Python: test |
| L3 to L5 | Leaf domains, the run-root hash domain, u64 coordinates and the branch-only citation are clarified in the next revision |

**Python reference after the fixes:** 45 tests (*measured*).

## 12. Program review (2026-10-03)

An independent adversarial review of the program implementation (rule 10)
found two highs, two mediums and two lows. The fixes:

| Finding | Fix |
|---|---|
| H1: the executor supplied the machine parameters (inputs, length) at COMMIT, bound only by its own run root | An LX1 run's 32-byte input id at `INIT_RUN` is the parameters' digest, so the payer admits them; COMMIT recomputes the run id with the committed digest and refuses a mismatch (test: `the_executor_cannot_commit_inputs_the_payer_did_not_admit`) |
| H2: the OUTPUT claim needed the claimed outputs' preimage, which the executor could withhold | The run commits only a digest; the claim opens the true output slots against `R_T` and C wins exactly when their digest differs from the committed one (test: `withheld_false_outputs_are_convicted_from_the_opening_alone`) |
| M1: empty positions and zero-slot transitions | A transition that touches no slot is the identity (E wins iff the roots agree). `transitions_in(p) >= 1` is an `LxMachine` contract that admitters check: an empty checkpoint interval cannot be opened, so a lie there would be undisputable |
| M2: windows are not sized from `k`, the interval or recompute cost | Admission condition (laws §9): the admitter sizes `phase_window` for the worst first-round recompute plus answer, and the challenge window for a full re-execution. D(N) for LX1 is not yet derived |
| L1: heap of an honest opening is unmeasured | Census item: measure the largest Basanos opening's heap on SBF before admitting its template |
| L2: Python and Rust differ on machine-bug paths (undeclared or duplicate writes) | Not reachable with a correct machine; recorded |

The four new account writers are reviewed and allowlisted. The LX handlers are
`pub(crate)`, so an embedding application cannot bypass the caller's checks.

## 13. Constants in openings (weights; built 2026-10-04)

The toy machine reads no constants, so the first program cut opened only state
slots. A Basanos transition also reads weight rows, which are template
constants (§2.3 item 2). They are committed per template and opened, chunk by
chunk, in the terminal replay.

**Commitment.**
- An LX1 template commits `constants_root` in the field that holds `spec_root`
  for descent templates. It is part of the template id. A machine without
  constants commits zero.
- `constants_root` is the root of a v2.1 tree of kind `lxconst` (node domain
  `dcg.lx.const.node.v1\0`, empty leaf `SHA256("dcg.lx.const.empty.v1\0")`).
  The leaf at position `constant_id` is
  `SHA256("dcg.lx.const.leaf.v1\0" || constant_id:u32le || digest)`; unused
  ids hold the empty leaf; capacity is the smallest power of two that is at
  least the largest id + 1.
- A constant's `digest` is the root of its v2.1 chunk tree (§4.2 of the v2.1
  design): `chunk_bytes = 2^v` per constant, leaves
  `SHA256("dcg.chunk.leaf.v2.1\0" || index:u64le || chunk)`, the last chunk
  possibly short.
- Committed constants are not on chain. The template's admitter names their
  availability source, as v2.1 does; templates are trusted subjectively and
  verified off chain.

**Machine.** `LxMachine::constants(p, i, reads, out)` fills the
`(constant_id, chunk_index)` pairs transition `(p, i)` reads, in order, and
returns their count. The default is none. `reads` are the read slots'
values, already verified against the agreed lower root, so a read chosen by
data (an embedding row chosen by a token, a lookup-table cell chosen by a
value) is a function of the committed state, never of the executor's choice
(data-dependent reads, 2026-10-04). `apply` receives the chunk bytes in that
order, after the slot values. `LxBound::max_transition` also returns the
most constant reads of any transition, which sizes the program's scratch.

**Machine contract.** For every reachable state, every declared
`(constant_id, chunk_index)` exists in the template's table and the count is
within `max_transition`. A read function that cannot name its reads for a
verified state (a malformed value, or more reads than its output buffer
holds) rules for the challenger, as a kernel failure does. Callers size
that buffer from `max_transition`, so on chain only a machine that breaks
its contract reaches this. (Follow-up: pin this case in the program goldens
with the Python forged-h checkpoint; re-review L-b.)

**Opening.** The staged replay opening (sub 25) is the state opening, then
`n:u32` and one entry per declared read, in order:
`len:u32 chunk  chunk_path_n:u8 hash*  digest[32]  const_path_n:u8 hash*`.
The ids and indices are not carried. For each entry the program checks:
- the paths are at most 48 (chunk) and 32 (constant) hashes long, and long
  enough to hold the index and the id;
- the chunk's leaf rebuilds `digest` through the chunk path;
- `digest`'s constant leaf rebuilds the template's `constants_root`.

A wrong count, order, chunk, digest or path is refused with error 50
(`LxRefusal::Constant`), after the state opening rebuilds the agreed root
(so a bad state proof together with bad constants returns 49). A count above
the machine's maximum, or a path length byte above its cap, is refused before
anything is read; chunks and paths are borrowed from the staged bytes, not
copied (review M1, L2). A section that runs past the buffer does not decode
(error 1 when cut inside a count or length field, 46 elsewhere); either way it
is a refusal that changes nothing. Nothing is ruled, and the executor may retry
before its deadline. The OUTPUT claim (sub 26) reads no constants.

**A template that commits other constants.** If the run's constants are not
under the template's `constants_root` (a wrong or zero root), no opening can
verify; the executor cannot answer and loses at its deadline. This matches
v2.1: the template, including its constants, is what the run is judged
against.

**Size.** One Basanos projection chunk reads 79,608 bytes of constants
(groundwork round 3, `attn_gate_proj_chunk`); this is already inside the
census's opening bytes and CU estimates. The two paths add `32·(h_chunk +
h_const) + 6` bytes per read, and two hash chains of those heights in CU.

**The heaviest opening (review M1).** The challenger can steer the bisection
to any transition, including the one with the largest opening. For an
application machine, the widest transition's state bytes, constant bytes and
paths must fit `MAX_STAGE`, the heap and the compute limit, measured on SBF
before its template is admitted; the opening window (`bytes_due`, §5) counts
the constant bytes. Otherwise an honest executor cannot answer and loses.

**Admission checks the program cannot make (review L3).** The machine
contract above (every reachable read exists and fits the maximum) is the
admitter's to check; it cannot be enumerated when reads depend on data. The
template's `constants_root` must be the table's root; the executor's client
refuses to commit a run when its own table root differs.

**Who profits by calling first.** Nothing changes: only the executor submits
the opening, and constant checks only refuse.
