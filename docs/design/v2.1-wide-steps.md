# v2.1 steps with many inputs (open design item, 2026-10-02)

**Status: owner chose B (list inputs), 2026-10-02; the list digest is a v2.1 tree (the recommended default). Python reference implemented 2026-10-03 (branch `fast/v21-list-inputs`, see below); not yet in the crate, wire format or program.**

## The limit

A v2.1 step has at most 8 input values (design §3.1). Its records grow
with its inputs:
- **`StepSpec`:** `192 + 72·n_in + 24·n_out` bytes, designed at most 1,024 bytes (§5.1).
- **Frozen v2.0 step leaf:** `64 + 28 + 2 + 55·n_in + 2 + 55·n_out + 64` bytes. The skeleton stores at most 1,100 bytes of leaf (`MAX_LEAF`), so at most about 16 inputs with one output.

## What Basanos needs

Compiler v1 operations read from up to 128 producer routes (the route
bound). The frozen revision-8 registry declares:

| Form | Declared `max_reads` |
|---|---|
| 22 | 106 |
| 10, 11, 12 | 50, 75, 104 |
| 19 | 69 |

Source: Basanos `docs/design/dcg-revision-8-2026-09-25.md`. In the K=10,240
fixture, the form-22 class 237 reads 36 producers, about 67 KB in total.

These operations already fit one transaction of *compute*: revision 8
measured 28 of its 29 forms in one transaction each, at most 1.2 M CU.
Their problem is the *number of edges*, not the work.

G1 (2026-10-02) ran real form-22 instances as one step by concatenating the
36 reads into one external input. That proves replay and staging. It does
not keep the instance's producer edges, so a lie in any one producer edge
would not be localized to that edge.

## Options

### A. Gather steps (no format change)

A tree of ≤8-input concat steps assembles the reads into one value, which
the operation then reads as one input. A 106-read operation needs 14 + 2 + 1
gather steps.

- **For:** no record or leaf change; every edge is an ordinary kind 1 edge.
- **Against:**
  - more steps and more trace;
  - the gathered bytes are copied up to twice, so the executor hashes them up to three times;
  - a dispute on a gather step carries up to the full gathered value as witness (64 KiB here);
  - the lowering has to insert the gather steps, an extra stage that has nothing to do with the model.

### B. A list input (new producer kind)

One input whose value is the ordered list of N producer ports. Its digest
is a v2.1 tree over the N element digests. EDGE(i, j) opens element j's
path and producer leaf j: one producer per claim. STEP's witness is the N
values, staged.

- **For:**
  - scales to any N;
  - claim openings stay one producer each;
  - the record grows by one list descriptor, not by N inputs;
  - faithful to the instance's edges.
- **Against:**
  - a new producer kind, list layout and digest, with goldens in three implementations;
  - admission checks each element's header agreement (linear in N).

### C. Raise the limits (no new concepts)

Allow up to 128 inputs per step.

- `StepSpec` reaches `192 + 72·128 + 24 = 9,432` bytes.
- The leaf reaches about 7.2 KiB.
- `MAX_LEAF` and the dispute record grow, and leaf reveals are staged (staging already reaches 128 KiB).

- **For:** the smallest conceptual change, since the frozen leaf format's `u16` counts already allow it; EDGE stays one producer opening.
- **Against:**
  - every opening of a wide step's spec or leaf costs about 9 KiB of staged data;
  - the dispute account grows for every dispute;
  - SHAPE compares up to 128 headers (cheap, but linear).

## Recommendation

**B (list inputs)**, if wide operations are common. In compiler v1 they
are: forms 10–12, 19 and 22 are on every layer of every position. It keeps
every per-claim cost independent of N.

**C** is the fallback if a new producer kind is unwelcome. It is simpler to
build, and the cost per dispute is about 10–20 KiB of extra staging,
roughly 15–30 more transactions.

**A** fits only as a stopgap; it inflates the trace for every run, not just
disputed ones.

## Questions for the owner

1. Choose B, C or A.
2. With B, should the list digest be a v2.1 tree (an element opens with a
   path), or a flat hash over the element digests (an element opens with
   all N digests: 32·N bytes, 3.4 KiB at N = 106)? The tree costs a little
   more to build and opens in `32·ceil(log2 N)` bytes.

## Python reference (2026-10-03, designed)

Branch `fast/v21-list-inputs`, `python/dcg/disputes_v21/` and
`python/tests/test_disputes_v21_lists.py` (16 tests, four planted referee
bugs each caught). Every choice below is **designed**, for owner review
before the crate and program follow.

- **Producer kind 8.** `a` is a list id. A list element is kind 1, 2 or 3 (a
  step output, an external input or a plain constant), 1 to 128 elements.
- **ListSpec (`DLS1`, spec type 10).** `list_id:u32 count:u32`, then per
  element `header(23) producer(24) pad(1)`: 48 bytes, 6,156 bytes at 128.
  ListSpecs are the last spec records, by list id, so a spec without lists
  keeps its bytes and root (the existing goldens only gain the empty `list`
  tree root). The program needs the first ListSpec index; the Python keeps
  it on the spec, and the template data does not carry it yet.
- **Step input.** Its header has layout 6 (LIST) and the elements' total
  length. Its digest is `H("dcg.list.v2.1" || count:u32 || root)`, where the
  root is a `list` tree over `H("dcg.list.leaf.v2.1" || j:u32 || ref_j)` and
  `ref_j` is the element's 55-byte value ref (its ListSpec header and value
  digest). The frozen leaf format is unchanged.
- **Leaf reveal binds the elements.** With a step leaf, E reveals each list
  input's element refs (55 bytes each, 7 KiB at 128, staged); the referee
  checks them against the leaf's list digest or refuses the reveal. Every
  later claim uses those refs, so `EDGE(i, j)` needs no element path.
- **`EDGE(i, j)`.** C opens the ListSpec and element j's one producer. C wins
  if E's element count differs from the ListSpec's, if element j's header
  differs from the ListSpec's, or if its layout fields or digest differ from
  the producer's (the ordinary kind 1, 2 or 3 rule).
- **STEP.** The witness for a list input is its element values, each checked
  against the revealed refs; the kernel receives them as separate inputs in
  order.
- **Honest challenger.** At a differing list input it names the first
  element whose ref differs from H's (or the first missing one).

**Open:**
- The alternative to the reveal: E answers an element-tree descent like the
  step tree's (C picks among revealed children), which costs rounds instead
  of a 55·N-byte reveal. The reveal is simpler and cheaper at N ≤ 128.
- Kind 5 (chunk) and kind 6 elements are refused for now.
- The crate mirror, wire encodings, golden vectors for DLS1 and the list
  digest, the program (tag 227 reveal and claim bodies), and SBF and live
  runs.
